# Open RTS 商业游戏开发计划书

> 目标：基于当前模板，6个月内完成一款可上架 Steam 的 RTS 游戏
> 人力：1人 + AI 辅助 | 时间：工作日 2-3h + 周末 4-6h ≈ 585小时

---

## 一、SC2 vs WC3 玩法对比与选型

### 核心差异分析

| 维度 | 星际争霸2 | 魔兽争霸3 |
|------|----------|----------|
| **单局时长** | 10-25分钟 | 15-40分钟 |
| **单位数量** | 50-150个 | 15-40个 |
| **TTK（击杀时间）** | 极短（秒杀成群） | 较长（单挑持续数秒） |
| **单位生存率** | 低（炮灰化） | 高（单位更珍贵） |
| **核心深度来源** | 宏操作（经济扩张、产能管理） | 微操作（英雄技能、单位走位、道具） |
| **英雄系统** | 无（只有特殊单位） | 有（等级1-10，技能3-4个，6格物品栏） |
| **中立生物** | 无 | 野怪营地（MF获取经验和道具） |
| **人口机制** | 200人口上限 | 100人口 + 低维护费/高维护费惩罚 |
| **分基地** | 多基地扩张 | 通常1-2个基地 |
| **科技树** | 线性升级 | 分支选择（如人族二本选法师或破法） |
| **道具系统** | 无 | 有（消耗品、光环、主动装备） |
| **昼夜系统** | 无 | 有（影响视野和某些单位） |
| **内容生产难度** | 高（需要大量单位和平衡） | 中等（英雄机制提供深度、单位种类较少） |

### 选型结论：**WC3 风格 + SC2 部分简化**

理由：

1. **WC3英雄系统**用极少的内容产生极大的玩法深度。1个英雄 + 4个技能 = 无限的可玩性。对1人团队来说，这是**内容生产效率最高**的设计。
2. **低单局单位数**意味着：性能压力小、网络同步容易（如果做多人）、AI 行为树更容易写、寻路负载低。
3. **较长的TTK**让玩家有操作空间，减少"一波定胜负"的挫败感，更适合休闲+核心之间的定位。
4. **模板已有基础**：双资源系统、双域导航、战争迷雾、建筑建造、AI框架、单位动作系统。WC3式的扩展更自然。

但同时采用 SC2 的简化思路：
- **不做100人口+维护费机制**（太复杂），改为固定人口上限（如60）
- **不做昼夜系统**（增加调试复杂度）
- **英雄等级上限5级**（降低平衡难度，WC3原版10级在实际对战中很少达到）

## 二、时间预算计算

```
每月 ≈ 4.3周
6个月 ≈ 26周

每周可用时间：
  工作日: 5 × 2.5h = 12.5h
  周末:   2 × 5h   = 10h
  合计:             ≈ 22.5h/周

总可用时间: 26 × 22.5 = 585小时
≈ 14.6个全职工作周（按40h/周算）
```

**时间分配原则**：
- 60% 核心玩法（战斗、经济、AI）
- 20% 内容和打磨（单位、地图、UI）
- 15% Steam上架（商店页、成就、测试）
- 5% 缓冲

## 三、游戏概念设计

### 游戏名称（暂定）：**Nexus Command**

### 核心卖点（3个关键词）
1. **英雄主导** — 每局围绕英雄成长展开，不是纯爆兵
2. **双阵营不对称** — 两个截然不同的种族
3. **紧凑战斗** — 30分钟内决胜负，适合碎片时间

### 世界观概要
科幻背景：两个派系争夺远古外星科技遗迹。

- **联邦（Federation）**：人类阵营，机械+步兵，偏向防守和阵地战
- **虫群（Swarm）**：异形阵营，生物+数量，偏向进攻和消耗战

### 核心系统清单

| 系统 | 优先级 | 说明 |
|------|--------|------|
| 双阵营 | P0 | 2个不对称种族，各8-10种单位 + 1个英雄 |
| 英雄系统 | P0 | 每局1个英雄，3个主动技能+1个被动，等级1-5 |
| 科技升级 | P0 | 攻防升级（3级）+ 关键科技解锁 |
| 经济系统 | P0 | 双资源（沿用模板），1个主基地起 |
| 野怪营地 | P1 | 地图上的中立生物，击杀获得经验和资源 |
| 道具商店 | P1 | 英雄可购买消耗品和装备（3-4种） |
| 战役模式 | P1 | 2个阵营各5关，共10关 |
| 遭遇战AI | P0 | 基于模板AI扩展，3个难度 |
| Steam集成 | P1 | 成就、云存档、排行榜 |
| 多人对战 | P2 | 仅LAN/P2P，不做匹配（超出时间预算）|

## 五、基于模板架构的实现路径

### 5.1 英雄系统

**新文件**：`source/match/units/Hero.gd`（继承 `Unit.gd`）

```gdscript
# Hero.gd 核心新增属性
var experience = 0
var level = 1
var skills = []        # Array[SkillAction]
var inventory = []      # 最多4格物品
```

**实现方式**：
- Hero 仍是 Unit 子类，复用所有 Trait 机制
- 技能作为特殊的 Action 子类（`SkillAction.gd`），有冷却、消耗、范围等参数
- 新增 `AbilityCooldown` Trait 用于显示技能冷却UI
- 经验获取：击杀单位 `MatchSignals.unit_died` → 检查击杀者 → 加经验

### 5.2 科技升级系统

**新文件**：`source/match/UpgradeManager.gd`

**实现方式**：
- 在 `MatchConstants.gd` 新增 `UPGRADES` 字典
- 升级是一个**全局效果**（影响该玩家的所有单位），不挂在单个单位上
- 升级在建筑（如"工程站"）中购买，消耗资源
- 升级生效：通过 `MatchSignals.upgrade_completed` 信号，受影响的单位动态修改属性

```gdscript
# MatchConstants 新增
const UPGRADES = {
    "infantry_attack_1": {
        "cost": {"resource_a": 3, "resource_b": 1},
        "time": 30.0,
        "effect": {"attack_damage": +1},
        "target_units": ["Tank", "Worker"],  # 受影响的单位类型
    },
}
```

### 5.3 野怪营地系统

**新文件**：`source/match/CreepCamp.gd`（继承 Node3D）

**实现方式**：
- 野怪营地是一个场景，包含一组中立单位 + 刷新触发器
- 中立单位使用现有 Unit 系统，但 `player = null`（没有阵营颜色）
- 击杀掉落通过 `MatchSignals.unit_died` → 检查是否是中立单位 → 给予击杀者经验/资源
- 刷新机制：营地所有单位被清空后，计时器等待 N 秒后重新生成
- 地图上放置多个营地，难度递增（离中心越近越强）

### 5.4 道具系统

**新文件**：`source/match/items/Item.gd`（Resource 子类）

**实现方式**：
- Item 是 Resource，不是场景节点
- 道具商店是一个建筑，点击后显示可购买道具列表
- 英雄 `inventory` 数组最多 4 格
- 消耗品（血瓶）：使用后立即生效并移除
- 装备（护甲）：挂载为 Trait，提供被动加成，直到被替换

### 5.5 战役触发器系统

**新文件**：`source/match/campaign/CampaignMission.gd`、`source/match/campaign/Trigger.gd`

**实现方式**：
- 每关战役是一个 `.tscn` 场景（本质上是一个特殊 Map）
- `Trigger` 是挂在场景中的节点，监听条件（单位到达、时间到达、单位被击杀等），触发事件（播放对话、生成敌人、改变目标）
- 过场对话：用 Control 节点显示立绘+文字，支持语音播放
- 过关条件：`MatchEndHandler` 扩展，支持自定义胜利/失败条件

### 5.6 Steam 集成

**实现方式**：
- 使用 GodotSteam 插件（GDExtension）或 godot-steam-multiplayer
- 成就：在 Steamworks 后台定义后，游戏内通过 `Steam.setAchievement()` 解锁
- 云存档：利用 Godot 的 `user://` 路径，Steam 自动同步
- 排行榜：通关时间、击杀数等数据上报

## 六、风险评估与应对

| 风险 | 概率 | 影响 | 应对措施 |
|------|------|------|---------|
| 英雄技能逻辑远超预期 | 高 | 中 | 每个英雄只做3主动+1被动，不做复杂交互（如位移、召唤物控制在W3前不做） |
| AI 行为树过于愚蠢 | 中 | 高 | 不追求"智能"，追求"有反馈"。困难AI通过经济作弊+单位属性加成来制造挑战 |
| 战役制作效率低 | 高 | 中 | 前3关做"教程级"（玩家只需要做一件事），减少脚本复杂度。先做战役框架再做内容 |
| 美术资源不足 | 中 | 高 | 全部使用 Kenney 免费模型+Asset Library资源。UI用程序化生成，不手绘 |
| 时间不够 | 高 | 高 | 砍掉 P2 特性（多人对战）。如果进度落后，砍战役关卡数（10→6） |
| Steam审核被拒 | 低 | 中 | 提前2周提交商店页审核，留足修改时间 |
| 失去动力/倦怠 | 中 | 高 | 每周末确保有可玩的版本（可运行比完美重要），用阶段性成果自我激励 |

## 七、可裁剪方案（如果进度落后）

- 战役 10关 → 6关（每阵营3关）
- 道具商店 → 只做3种消耗品，不做装备
- 野怪营地 → 只做2种（弱/强），不做精英营地

- 取消战役，只做遭遇战（AI skirmish）
- 取消道具系统
- 取消野怪营地
- 英雄技能减到2个
- 专注做**最核心的"英雄+兵种克制+科技"**体验

## 十、总结

**关键决策回顾**：
1. **WC3风格** — 英雄驱动的深度 > 暴兵的数量
2. **2个阵营** — 做深不做宽
3. **单机优先** — 战役+AI对战覆盖90%的玩家需求
4. **最大时间杀手识别**：多人对战（砍掉）> 战役脚本（简化）> AI（用参数作弊代替智能）

**核心原则**：宁愿做一个内容少但完成度高的游戏，也不要一个内容多但到处是半成品的游戏。Steam 玩家对独立游戏的第一印象来自"是否完成"，而非"有多少单位"。

585小时，一个英雄RTS，可以做到。
